# 从新环境到可靠结果

本页面向已取得资源使用授权的人。开始前先读 [agent-start-here.md](agent-start-here.md)。不会自动创建资源或替你批准预算。下面每个阶段要读完结果再进行下一阶段，不能连成“安装→试跑→默认批准→生产”的无人审阅链。

## 1．复用资源，分清虚拟机与集群

进入学校门户，确认已有项目、实例、镜像、GPU 型号和有效期。先看已有任务再选择实例；“看不到自建实例”可能是资源在老师/共享项目下，不代表必须充值个人账户或创建新实例。

记下实际资源规格、获准预算、计费周期、预计最长运行时间。GPU 闲置或退出浏览器通常不自动停止计费；是否停止、关机或释放后仍收存储费由当前平台规则决定。

本次历史部署是一台 Ubuntu GPU 虚拟机；不是向通用学校调度器提交作业的演示。如果当前入口是 Slurm/PBS 集群，先获得正确 allocation，并遵循学校队列规则；不要在登录节点运行 CUDA/CPU MD。

## 2．驱动与 GPU：先验证实际绑定

先运行 `nvidia-smi`，读取型号、驱动及错误。需要进一步诊断时，只读检查 `lsmod`、内核日志和 GPU 设备驱动绑定。包管理器说“安装成功”不等于内核已加载正确驱动。

本次历史上曾装好 `nvidia-driver-580-server`（580.178.04），但 GPU 仍被 `nouveau` 绑定；重启既有实例并重新登录后才继续验证 NVIDIA 驱动。**这是特定镜像上的已验证修复，不是让所有用户执行驱动升级或重启的通用处方。** 修改驱动/重启前须核对当前作业、备份、资源授权及学校管理员要求。不要自行修改共享计算节点的驱动。

`nvidia-smi` 显示的 “CUDA Version” 是驱动支持能力信息，不等于当前 Python 环境装了该 CUDA runtime，更不等于所有旧 GPU 支持最新工具链。

## 3．独立环境与版本指纹

本次 V100S（Volta/sm70）部署使用 CUDA 12.x 环境；2026 年 10 月的历史记录为：

| 项目 | 本次记录 | 解释 |
|---|---|---|
| 系统 | Ubuntu 22.04、Linux x86_64 | 不等于其他镜像已测试 |
| Python | 3.11 | 与包构建匹配 |
| OpenMM | 8.6.1，conda 构建 `py311h6619805_0` | 当时 Linux CUDA 12 构建；同版本另有 CUDA 13 构建 |
| CUDA runtime | 12.9；NVRTC 12.9.* | 针对 V100 和该 OpenMM 构建核实 |
| NumPy | 2.4.6 | 历史环境指纹的一部分 |

不能只写 `openmm=8.6.1` 就认为环境完全相同；也不能复制本机 Windows/OpenCL 环境到 Linux/CUDA。安装前查当前包元数据、GPU 架构和驱动兼容性，先 dry-run 检查依赖，再固定关键构建。上述版本不是永久推荐锁文件。

优先复用可用 conda/mamba，建立任务独立前缀，不替换系统 Python。若确需引入管理器，使用官方来源并校验发布方 SHA256；安装到工作目录，不做无关 shell 初始化。部分安装或已有目录先审阅，不覆盖、删除或放宽版本约束重试。

本次输入已经参数化，运行只需 OpenMM、NumPy 及运行器实际依赖，不必在远端重新安装整个 RDKit/OpenFF/Torch/NAGL 工作栈。需要后处理的库放在单独分析环境，避免更新正在运行 MD 的依赖。

保存软件版本、驱动/GPU、`conda list --explicit` 或等价已安装清单，并对清单和执行脚本做 SHA256；记录代码 commit。依赖求解计划与实际安装清单可能不同，两者都保留。环境哈希有助于辨认内容，不自动保证二进制 checkpoint 可跨平台读取。

依次区分：导入成功 → CUDA 平台列出 → 实际 Context 运算成功 → 真实体系 pilot 成功。前一步不能替代后一步。本次曾用两个粒子的已知能量做 CUDA Context 技术检查；它不推进动力学，也不是配体结合验证。新探针 `hpc_probe.py` 连这个 Context 都不会创建。

## 4．准备、上传和冻结输入

只传执行所需的最小包，不传环境缓存、全项目资料、密码文件或无关文献。上传完成后比较本地与远端 SHA256，再验证压缩包 CRC 和逐文件清单；解压到全新目录，禁止覆盖已有 run。

输入审计需覆盖：

- 蛋白来源、缺失/补建区域、突变、质子化、结晶水的处理。
- 配体化学图、立体化学、氢、形式电荷、部分电荷来源与和。
- docking/晶体起点究竟是哪一份结构；不要把旧选择姿态重新命名为新 top1。
- `system.xml`、拓扑、位置数组的原子顺序、粒子数和盒矢量。
- 力场、约束、barostat 和位置约束参数是否符合运行器协议。

格式见 [MD 输入契约](../md-execution.md)。本仓库不含真实系统，不能只上传某个 SMILES 然后调用执行器就宣称准备完成。预训练电荷估计也不得改称本次量子化学计算。

## 5．实际 pilot 与人工技术审阅

在正式使用的学校环境、正式冻结输入上运行短 pilot；单 GPU 串行安排。先检查已有同 case/seed 身份和进程，避免重复。

本次历史 pilot 为短暂递减约束平衡加短无约束采样。应读取完整质量报告和必要原始证据，而非只看 exit 0：

- 能量/坐标/温度/密度是否有限，有没有 NaN、崩溃或异常穿插。
- 蛋白、配体、补建片段的最终几何；先处理周期边界、再对齐蛋白。
- 温度/密度的整体范围和短平衡瞬态，不能把几十 ps 当作收敛证明。
- 实际吞吐量、初始化开销、磁盘估计。

只有真正读过这些内容，才用 `review` 写审阅者、具体理由和四项已检查标志。不得把“审阅开关全勾”用作自动通过机制。详细命令见 [scripts/README.md](../../scripts/README.md)，不要在未准备输入时复制生产模板执行。

## 6．正式队列、防重复和监控

先固定有限任务清单：case、seed、平衡长度、生产长度、顺序、对应 pilot 审阅与预算。使用后台会话/学校调度器运行，完整保存 stdout/stderr、启动回执和进程身份；不要依赖网页终端一直连接。

队列应有明确 `status`、互斥锁、防重复登记、已有进程检查和失败即停行为。启动操作必须显式，不应默认 `start`。**实际旧包装器曾有默认启动行为，因此新 agent 不能猜其默认值。** 本仓库的数组入口只运行清单中的一项，它本身不是完整远程调度服务。

每轮只做一次必要快照；检查有限日志/CSV 尾部、速度、GPU、磁盘、身份和检查点。后台实时写入与监控竞争时，读取失败先标暂不可读。不要凭 ETA 标记完成，或因页面过期提交第二份队列。

历史生产速度随体系不同，约为数百 ns/天量级；应使用当前真实任务的 ns/天估计。生产耗时约为 `目标 ns / 实测 ns每天 × 24 小时`，另加启动、平衡、分析和备份；硬件名相同不保证速度相同。

## 7．checkpoint 与有效轨迹

双槽 checkpoint 是二进制内容加哈希元数据，必须对应同一输入、平台、软件版本、seed、协议和目标步数。不能跨 CUDA/OpenCL 或机器环境随意续接，不能修改身份 JSON 来骗过检查。

检查正在更新的槽时，先读 metadata，再读 checkpoint 并哈希，最后再读 metadata；若前后不同，记录写入竞争，有限重试后仍未知就保留未知。只验证一个 SHA 没有同时核对身份和步数是不完整的。锁文件存在可能正常，锁文件本身不存在也不能替代进程审计；不要盲删锁。

恢复会产生独立 attempt，一部分旧尾帧可能被替代。**分析必须按 `segment_manifest.json` 有效片段执行，不能把所有 DCD 直接相连。** 完成状态至少核对 summary、completed attempt、目标步数与身份哈希。检查点完整不等于轨迹质量合格。

## 8．WebDAV：本地权威文件，共享发布副本

本次共享盘上一次 `os.replace()` 原子改名失败，导致后处理包装器在启动 worker 前写状态失败。解决方法是：在 VM 本地文件系统先写临时文件并原子替换作为权威状态；共享盘只发布普通写入的副本，镜像失败单独报错，不改变 MD 结果。

普通共享写入可能让读者看到半份 JSON，且镜像可能滞后；验证 JSON、内部时间和来源。不要假定所有 WebDAV/网络文件系统都支持与本地相同的 POSIX 语义。这次问题不是 MD 数值失败。

带空格/括号的挂载路径应整体加引号。上传尽量走平台文件接口，小文件校验后用一行短命令启动；不要经 VNC 键盘发送整份 Python、长 base64 或多层 shell 转义。

下载接口超时时，本次用网页文件编辑器打开完整 JSON、聚焦实际代码区域、全选复制后从浏览器剪贴板读取成功。应确认读到的是有效完整 JSON，只读打开不保存编辑；编辑器结构依页面实际情况，不固定 CSS、tab ID 或坐标。下载失败不能自动推定为认证失效。

## 9．分析与可核验备份

完成轨迹在隔离分析环境中处理，保留 PBC、蛋白对齐、氢键距离/角度、重原子接触和起点审计。检查有效帧数、覆盖区间、重复/缺失。运行中分析必须标明不完整快照，最终仍需重新分析。旧的单母药后处理程序不能盲套新候选或新 seed。

归档原 run、输入、协议、软件/代码指纹、技术审阅和分析输出；避免相同 basename 的文件覆盖（例如审阅 JSON 和配体 JSON），保留各自目录前缀。归档过程：

1. 确认源任务已完成且身份匹配；列出有限归档清单。
2. 保存每个源文件 SHA256，创建新归档，不覆盖已有归档。
3. 检查 ZIP CRC、成员数量/路径，并逐成员比较 SHA256。
4. 重新哈希源文件，确认归档期间未变化；只对稳定源声明完成备份。
5. 计算归档 SHA256，复制到共享目录，再独立哈希副本。
6. 回执记录每一步结果。学校共享副本通过不等于控制电脑已经下载成功。

大文件传输和压缩也需预留磁盘。早期仅有截图中的哈希而无法可靠转录时，保留截图并明确“未取得机器可读哈希”，不能编出字符串。CRC/哈希用于完整性，不证明结果科学正确。

## 10．交付与资源结束

交付分四个状态：采样完成、分析完成、科学审阅完成、备份通过。记录尚未解决的通道/数据问题、谁接手和最后真实观察。截止时停止自动跟进，不自动延长预算；已有后台队列是否停止须单独有证据。

资源释放前先确认原始结果与必要 checkpoint 的可核验备份、后继负责人和平台计费规则。若当前授权只覆盖查询/整理，不擅自关机、删除实例或延长租期。数据齐全后按获准操作结束资源并保存最终计费/释放回执。
